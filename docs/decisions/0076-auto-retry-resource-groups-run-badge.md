# ADR-0076：链内自动重试、资源组互斥与运行状态统一标识

日期：2026-09-30。状态：采用。

## 背景

多项目批量运行暴露三个问题：

1. 下载并发 (download:2) 下某项目下载失败后链即挂起，即使其余项目已让出并行槽位，失败项目也静默等待人工处理——网络/代理类瞬时失败本可自动恢复。
2. 音轨分离与语音转文字可同时运行（各自 1 个并行槽），二者都重度占用 GPU/CPU，争用导致双方性能骤降甚至双双超时。步骤级并行度无法表达「不同步骤抢占同一资源」。
3. 项目列表中「正在自动流程中」与「空闲」的项目在视觉上无法区分；链/全流程状态散落在各页面，表达方式不统一。

## 决策

### 1. 链内失败自动重试

`runner.step_retries`（每步骤次数，默认 `download: 1`，0=维持失败即挂起）+ `runner.retry_delay`（默认 15 秒）。仅对 **active 链的链头**生效：失败时保持 failed 状态可见（suggestion 注明「将自动重试 (第 n/N 次)」），延迟后经完整 `start_step` 门禁重新入队；重试成功则链自然继续，额度用尽走既有挂起路径。用户取消（`cancel_step` 返回 `retry_cancelled`）或强制结束撤销重试计划；用户在等待期手动重跑时，重试线程检测到步骤已在运行即退出，不竞争。计数在 600 秒窗口内跨重试累计（修掉了「重启计数导致无限重试」的实现陷阱）；超时/用户取消/未预期异常不自动重试。实现为 daemon Timer，等待期不占并行槽位与线程池——失败项目的下载槽位立即让给排队项目，这正是「失败重试也并行」的形态。

### 2. 资源组互斥

`runner.step_resources` 把步骤映射到资源组（默认 `preprocess/transcribe/tts → gpu`），`runner.resource_concurrency` 定组上限（默认 gpu:1）。并行槽位键从步骤名改为资源组名：同组步骤即使分属不同项目也同时只能执行一个；未分组步骤保持 `step_concurrency` 各自额度。改组员/上限实时生效（每次获取槽位时重读配置）。

### 3. 运行状态统一标识

- 项目视图新增轻量 `workflow_status`（最近一次 WorkflowRun 的状态，单行索引查询）。
- 新组件 `AutoRunBadge`：⚙ 自动流程（忙碌/监测/待继续，info/success/warning）> ⛓ 续跑中（active 链，可拼当前步骤名）> ⏸ 自动运行已挂起 > 🔄 手动单步。用于项目列表卡片（替代原 🔄 标签）与步骤页页头（与步骤状态标签并列）；总览页的 ChainStatus 横幅沿用同一 ⛓/⏸ 图标与 info/warning 配色，构成统一视觉语言。

## 已知约束

- gpu 组串行会降低吞吐（TTS 长任务期间其他项目的 GPU 步骤排队）；显存富余可调大 `resource_concurrency.gpu`。
- 自动重试仅链内生效：单步手动运行的失败仍需人工处理（显式哲学）。
- 列表 `workflow_status` 只取最近一次运行；历史运行状态在总览「自动运行」卡查看。

## 验证

`test_runner_resources.py`：重试后成功并继续链（修诱因）、额度用尽挂起、等待期取消保持失败、跨项目 gpu 互斥（preprocess+transcribe 峰值并发=1）、项目视图/列表透传 workflow_status。全量后端 1329 项、前端测试与构建通过。
