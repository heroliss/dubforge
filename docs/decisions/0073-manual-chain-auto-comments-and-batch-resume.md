# ADR-0073：手动链支持评论自动采集与跨项目批量恢复

日期：2026-09-29。状态：采用。

## 背景

设置项 `comments.mode` 提供「自动采集、评分和翻译」(auto) 模式，但该语义只在完整工作流引擎里生效（合成前插入 comments 步骤，自动保存上屏方案，见 `workflows._comments`）。手动勾选链（「核对运行步骤」「运行本步」）完全不读取该设置：只要成片版本含评论且无已确认方案，启动即报「请先在评论精选中确认上屏内容」。批量跑多项目的用户设了 auto 却仍被逐个拦截，且该拦截发生在链头步骤启动时，表现为一闪而过的弹窗，无法从批量入口恢复。

同时，工作流引擎的失败恢复只能逐项目操作（「检查并继续流程…」），多项目批量失败时没有批量入口。

## 决策

### 1. 手动链复用自动采集（评论准备=auto 的一致语义）

- 抽取 `dubforge/comments_auto.py`：`prepare_overlay`（采集→评分→翻译→按评分挑选→保存上屏方案，零条可用即 `COMMENTS_AUTO_EMPTY`）与 `spec_from_config`（从配置作用域推导规格）。工作流引擎的 `_comments` 重构为调用同一实现，行为与文案不变（时长探测仍用 `service._probe`，测试桩依赖它）。
- `runner._start_step` 组装默认合成任务时，`confirmed()` 抛 `COMMENTS_NOT_CONFIRMED` 且 `comments.mode=auto` 且来源为 YouTube → 不再拦截，任务标记 `comments_auto=True`；其余情形维持原拦截。
- `version_render.run` 开头处理 `comments_auto`：磁盘上仍无已确认方案则执行自动准备并写入日志；随后**带方案重新解析全部版本规格**，保证运行内指纹与实际渲染输入一致。已有方案时直接复用（不重复采集，维持幂等）。
- 确认语义不变：auto 模式是用户对「机器挑选上屏内容」的显式授权（与工作流引擎同一前提）；方案保存后仍可在评论精选页人工重审。saved 模式（默认）依旧要求先人工确认。

### 2. 跨项目批量恢复失败的自动流程

新组件 `BatchWorkflowResume`：逐项目 `GET /workflow/status` 找最近一次 paused/failed/attention 且未投稿的运行 → `POST /workflow/plan`（携带 resume_id）预检 → 一次确认后逐项目 `POST /workflow/{id}/resume`（携带预检配方与指纹，confirmed=true）。复用现有端点，不新增后端面；预检未通过的项目在抽屉中显示原因，不带病恢复。入口位于项目列表选择栏「继续失败的自动流程…」。

### 3. 批量重试文案动态化

项目列表的「核对并运行当前列表待处理项目…」在当前视图存在失败项目时变为「重试失败项目（N）…」，且目标收敛为失败项目；无失败项目时保持原语义。

## 验证边界

后端新增 `test_comments_auto.py`：auto 模式手动合成自动准备并渲染（真实 FFmpeg + 桩采集/LLM）、二次运行复用方案且指纹跳过、saved 模式维持拦截、零条可用明确失败不保存空方案。工作流自动评论套件（test_workflows/test_workflow_media）验证重构无回归。前端新增 `batchWorkflowResume.test.ts`（可恢复筛选、预检指纹携带、失败不中断、显式确认文案）。全量回归见提交说明。

## 已知约束

- 自动采集仅支持 YouTube 来源；本地视频维持人工确认路径（与工作流引擎一致）。
- 手动链的自动准备发生在合成步骤内：采集与 LLM 评分/翻译计入合成步骤耗时与日志；超时兜底按合成步骤配置计算。
- 批量恢复依赖逐项目预检，发布模式项目会查询B站元数据，项目多时抽屉检查需要等待。
