# 0224：执行诊断累计时间与活动时间分开

日期：2026-10-20

状态：采用

## 背景

`Recorder` 的 `started_at` 从本轮任务受理开始，诊断 `elapsed_seconds` 按该起点计算累计时间。运行器的活动时钟在取得资源时开始，并扣除协作暂停。然而 `execution_details` 曾把正在运行任务的诊断累计时间覆盖为活动时间，导致排队转运行时耗时减少、上下文移除后又回到累计值。持久化记录与内存记录因此具有不同口径。

## 决定

- `execution.elapsed_seconds` 始终遵守 `execution.started_at`，由同一套 `Recorder` / `normalize` 计算本轮累计时间，包含排队与协作暂停等待。
- `Step.elapsed_seconds`、进度提供器和 ETA 保持活动时间口径；活动时钟在取得资源时开始，排除协作暂停，不改变估算算法。
- 轻量执行接口、步骤详情和项目列表统一调用运行器的诊断投影，不再根据内存上下文是否存在覆盖诊断累计时间。
- 终态诊断按已记录的结束时间冻结。只有生产者明确写入 `paused` 的诊断记录采用现有暂停终态冻结规则。普通 `check_pause` 只维护活动时钟与日志，没有创建暂停诊断阶段；本次不改变这个生产行为或调度。
- 明确继续并创建新轮次时，沿用既有 `Recorder(restart=True)` 契约重置本轮起点，保留旧阶段历史。

## 验证

隔离测试通过实际 `StepContext`、`_begin_running`、`check_pause` 和三个只读 API 投影核对同一任务：排队 2040 秒后运行 107 秒，诊断累计为 2147 秒、顶层活动时间为 107 秒；协作暂停 300 秒期间累计为 2447 秒、活动时间仍为 107 秒；恢复 10 秒后分别为 2457 秒和 117 秒。终态及上下文移除不再改变口径。另覆盖显式暂停诊断冻结、丢弃旧任务上下文时不能借用其耗时。

测试只使用隔离数据目录和受控时钟，不启动模型、不启动测试服务器，也不修改生产任务或正式产物。
