# 0189 自动制作与原BV更新的统一确认

日期：2026-10-17

## 问题

原稿已被退回时，用户必须先合成，再到发布记录选择新成片并启动更新。普通自动投稿出于防重保护拒绝已有发布记录，不能简单把此拦截移除：这会产生第二个BV，且旧稿审核状态和旧CID章节容易被错误复用。

## 决策

- 单项目新增每次运行意图 `mode=update`。它不成为全局默认，也不改变普通 `publish` 防重合同。总览、项目空间和原稿记录进入同一个预检及确认界面。
- `recipe.update` 明确原发布记录和 `old_cid → version_id` 对应关系。只有版本ID、原上传回执和精确产物ID/哈希能证明关系；历史快照缺版本ID时使用成功版本登记补证。证据不足必须人工选，不能按同名、时长或位置猜测。
- 确认冻结原账号、BV、原记录revision、远端version、完整有序分P清单、版本映射、明确保存的文案和章节/合集范围。展示名称及获取时间不参与业务指纹；启动锁内离线重算复用已核对远端快照。
- 制作沿用正常依赖规划和配置生效规则，只补齐必要步骤。成片必须经过本次版本解析和新鲜度核验；有效转写、翻译和配音复用，用户精调不自动覆盖。完全未变的成片不进行无意义重编码，合法原片直用版本绑定已登记的原视频及哈希。
- 制作后以 `plan.assembled_versions` 中本次实际成功的产物建立 `PublicationUpdate`，固定ID为 `workflow-update-<workflow_id>`，并以请求摘要核对重放，封闭落库与父流程关联间的中断窗口。父流程在 `plan.publication_update_id` 持久关联，不让进度Recorder覆盖此身份。
- 内部 `workflow_id` 参数只接受实际持有本项目租约的线程。HTTP接口不能传入此权限。制作期间原稿远端版本、分P顺序、源章节资料变化时，上传前暂停并要求重新核对。
- 复用既有原稿更新执行器：上传→原BV换片→等待新视频审核/转码→按新产物的成功剪辑快照映射章节→绑定新CID→同步合集→回读。源章节使用本次项目设置，平台章节硬约束仍由既有整理/校验逻辑执行。
- 只用当前项目明确保存的可同步文案覆盖远端；默认空值不能擦除远端已有内容。未选择目标合集时保留原归属。所列章节范围明确授权覆盖被替换分P的章节。
- 父流程独立投影子更新任务的状态，不使用旧稿“已通过/已退回”推断本次完成。暂停、继续、重启恢复均保持固定任务；已上传/已确认修改不重复发送，未知写入仅核对，章节失败仅续章节等未完成交付。
- 恢复预检指纹绑定子任务身份、状态及冻结方案。已建立子任务后不重新制作，界面明确显示未完成交付；核对unknown与执行retry分开。
- 原记录的平台状态观察属于辅助刷新，刷新失败显示单独提示，不推翻已经完整回读核验的更新结果。

## 验证边界

新增领域与编排回归覆盖精确映射、历史映射恢复、固定更新ID、真实租约、远端及章节变更门禁、原片直用、未知结果、失败恢复和辅助回读失败。前端覆盖单项目入口、多原稿选择、映射编辑、统一确认及恢复语义。

8611隔离网页以12秒视频执行真实本地制作，使用假账号、假上传/平台和假章节模型，经过真实更新/章节状态机，确认章节绑定新CID；恢复阶段未再次上传或换片。此验收不等于真实账号更新成功。真实第二项目只做读取和预检，未执行上传、投稿或修改。

## 取舍

当前不自动推断跨项目批量换片目标，不自动裁剪驳回片段，也不宣称重新合成能保证审核通过。内容修正需在项目中明确配置；成片和章节随后使用同一成功时间轴。
