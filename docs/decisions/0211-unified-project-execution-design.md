# 0211：以交付目标统一项目运行入口

状态：已实施；执行与界面验收见 data/diagnostics/project-execution-20261019/acceptance.md

日期：2026-10-19

## 问题与现状

总览的步骤勾选、运行入口的执行方式和完整流程抽屉正在承担重叠职责。

- `ProjectRunPanel` 的“按当前勾选运行制作”使用制作链，只处理制作，不读取发布终点。
- `WorkflowPanel` 的“设置本次流程”又选择一次制作范围和最终交付。
- `PipelineView` 的制作勾选是持久的 `auto_steps`，发布勾选却只是页面内的临时意图。
- 批量完整流程还有独立范围和终点选择，可能与单项目设置不一致。
- 发布步骤已经保存 `run.mode`、账号、分P、文案和章节等设置；`configuration.run_spec()` 本来就约定从同一设置推导执行输入。

因此，这不只是按钮文案相似，而是用户需要理解多套执行入口及其不同覆盖规则。

## 设计原则

1. 步骤页保存业务设置，项目总览负责启动和观察。
2. 正常项目运行由期望的成片和发布目标反推必要步骤，不要求用户手工维护技术依赖链。
3. 执行前显示实际方案并确认，不在确认页再维护一份可编辑的项目配置。
4. 单步操作、现有文件上传和历史任务恢复保留各自明确边界。
5. 每次远程动作必须符合本次明确确认的账号、目标和交付方式；修改当前默认设置不能扩大历史任务的发布授权。

## 正常项目运行

```mermaid
flowchart LR
    A["步骤页保存参数与交付目标"] --> B["总览：运行项目"]
    B --> C["检查实际执行方案"]
    C --> D["确认执行"]
    D --> E["按交付目标结束"]
    C -->|"需要修改"| A
```

用户在合成页选择项目需要的成片版本，在发布页设置交付方式。点击“运行项目…”后，系统列出所需工作：

- 已有效的结果：复用。
- 缺失或需要更新的结果：制作。
- 所选目标必需的上游输入：明确列入依赖补齐。
- 不参与所选目标的功能：跳过。例如纯原声直用版本不应因为历史全流程默认值而无条件转写、翻译和配音。

预检中的范围是系统解释“这次实际上会做什么”，不再是第二份范围配置。需要改参数或交付方式时，直接返回对应步骤；回来后重新检查。

## 页面职责

| 页面 | 可以设置或执行 | 不再承担 |
|---|---|---|
| 各制作步骤 | 本步骤参数、可选处理，以及明确的局部运行命令 | 另一份项目技术步骤勾选 |
| 合成成片 | 版本定义、持久的项目目标成片清单、单版本预览和重做 | 账号、投稿终点、另存一套全流程范围 |
| 发布到B站 | 交付方式、目标稿件、账号、分P、文案、章节与更新范围 | 让总览再勾一次“包含上传” |
| 项目总览 | 项目目标摘要、运行项目、查看进度、继续任务 | 编辑制作范围、覆盖发布终点 |
| 执行预检 | 生成、复用、依赖、目标账号/BV、确认动作 | 再选“全部/选定/不制作”、再选是否投稿 |
| 批次运行 | 项目顺序、并发、失败暂停等跨项目调度 | 用临时范围或终点覆盖每个项目的步骤设置 |

“制作三个版本、发布其中两个”仍然是两个不同业务选择，分别由合成页与发布页保存。版本定义的存在、历史生成文件的存在，不代表该版本必须成为本次项目的制作目标。

## 合成目标与技术步骤

正常项目运行取消总览的技术步骤勾选。不能仅把同一排开关搬到九个步骤页。

合成页应将“项目目标成片”保存为稳定的版本ID集合。现有 `AssemblyVersionWorkspace.selected` 只是本次手动生成的页面状态，不能直接冒充项目设置，也不能取“所有历史版本”作为默认制作目标。

规划器根据目标版本的原声/配音、字幕和评论需求解析依赖。界面仍展示九个业务阶段，内部任务拆分由系统处理。评论是否参与依赖版本输出与评论步骤设置，不额外添加与版本评论开关矛盾的流程开关。

“项目目标成片”和“发布分P清单”保持不同职责：

- 仅制作时，以合成步骤保存的目标成片为准。
- 自动制作并发布时，还要确保发布清单要求的成片可交付；预检明确说明额外需要补齐的目标。
- 临时重做某个非项目目标版本，使用“仅生成此版本”，不为此改写项目目标。

## 发布步骤作为唯一发布设置来源

发布页使用一个交付方式选择，不同时维护 `enabled`、`auto_upload`、`auto_publish` 等相互组合的独立开关。

推荐对用户展示四种终点：

| 交付方式 | 明确结果 |
|---|---|
| 仅保留成片 | 制作完成后结束，不进行发布准备或远程上传 |
| 准备发布草稿 | 整理本地稿件资料，随后由用户处理上传与投稿 |
| 上传后等待确认 | 上传选定文件，停在可继续确认的状态，不自动提交新稿 |
| 上传并提交 | 按本次确认的目标创建新稿或提交原稿更新 |

`run.mode` 保留 `produce/draft/publish`，新增独立 `upload` 值；新稿和原稿更新均保存真实上传就绪状态，由明确提交动作增加投稿授权，普通恢复或重试不会提升权限。

目标稿件也在发布步骤选择：

- 更新已选原稿：保存本项目的明确目标及更新范围意图，保留原BV。
- 创建新稿：明确展示将生成新BV；已有稿件时仍需确认另发新稿。

原稿目标不能作为全局或模板继承值。多个可用BV时必须选定目标，不能根据“最近一个”猜测。每次预检重新读取远端分P与CID并校验映射；不能永久沿用上次更新前的CID。

发布意图中，替换视频、文案、章节与合集各自有明确范围。未选内容保持远端当前值。“只上传后等待”若应用于已有稿件，只能准备替换文件，不得提前调用稿件编辑提交；用户确认后才提交替换与所选同步范围。

## 总览与确认页

总览只保留一个正常入口“运行项目…”。无中断任务时直接进入预检，移除“按当前勾选运行制作／设置本次流程”二选一。

总览以只读摘要展示项目目标版本、发布终点与发布目标，并提供进入相关步骤的链接。运行中主入口变为“查看进度”，提供停止或暂停操作。

预检必须让用户能判断：

- 会制作哪些版本，哪些有效结果可以复用。
- 会补哪些必要依赖，以及补入原因。
- 是否上传、是否提交，目标账号、新稿或具体BV。
- 替换哪些分P，是否同步章节、文案和合集。
- 运行后停在哪里，是否还有一次人工投稿确认。

确认按钮随动作使用“确认运行”“确认运行并上传”“确认运行并投稿”“确认更新原稿”等具体文案。未确认前不启动制作、上传或远程写操作；预检可以做必要的只读远端核对。只保留最终必要的确认，不串联多轮同义弹窗。

## 局部操作与恢复

局部操作是明确命令，不是另一份项目配置：

- **仅运行本步**：只处理当前步骤，不接上项目发布终点。
- **运行到本步**：补齐该步必要输入并停在该步。例如只需要转写结果时可用。
- **从此继续项目**：以此为明确起点，检查必要输入与下游目标，仍使用发布步骤保存的终点。
- **仅生成此版本**：只做这一份成片，不因为项目启用了发布就自动上传。

“从此继续”也不应无条件强制重做全部后续结果；有效结果复用，需要强制重做的破坏性操作由对应步骤明确提供。

有中断记录时，保留两个有不同含义的入口：

- 继续上次任务：沿用上次确认的范围、目标和发布授权，检查剩余工作。
- 按当前设置重新运行：读取当前步骤设置，生成新的执行记录。

两者展示上次与当前的关键差异，不能因后来启用投稿就让旧的仅制作任务在恢复时自动投稿。已经开始上传或提交的任务复用既有回执和文件；结果未知先核对，不重投。

执行范围、发布授权和目标属于已确认计划；普通步骤参数在排队状态仍按现有运行时编辑机制处理，取得执行槽进入运行状态时才冻结本步实际消费的字段。合成版本规格等已冻结内容，以及项目结构与目标授权，仍遵守各自的门禁；不能把“排队时可调普通参数”扩大成所有内容均可变，也不能通过本次交互改造把所有参数提前锁死。

## “只上传”与“只同步”必须独立成立

“只上传现有成片”不能用“尽量复用的完整制作流程”替代。

发布页选择具体成片后，冻结其产物ID、哈希与成功快照，直接检查发布条件。它不反推重新制作，不因为工作稿变化而触发转写、TTS或编码，也不替换成另一个更新的文件。

同理，只更新文案或章节的原稿任务没有视频制作目标，不要求当前制作版本最新、源视频仍存在或TTS服务在线。章节使用实际已上传分P的时间轴证据；要替换视频时才绑定新成片快照。

## 典型场景

| 用户目标 | 设置或入口 | 实际执行 |
|---|---|---|
| 只制作成片 | 合成页选目标，发布页选仅保留成片 | 检查需要的依赖，制作后结束 |
| 制作后上传，稍后投稿 | 发布页选上传后等待确认 | 制作/复用目标，上传后停止 |
| 制作后自动投稿 | 发布页选上传并提交、明确新稿或原稿目标 | 一次预检确认后执行至对应提交与交付阶段 |
| 上传已生成文件 | 发布页选择现有成片并上传 | 固定具体文件，不进入制作链 |
| 只要转写结果 | 转写页选择运行到本步 | 补齐输入并停在转写 |
| 修改字幕后更新原BV | 字幕与合成设置保存，发布页选择原稿及替换范围 | 更新必要产物，替换指定分P并同步所选内容 |
| 仅更新B站章节 | 发布页原稿更新只选章节 | 按已上传视频的快照处理，不启动制作 |
| 继续失败任务 | 继续上次任务 | 核对剩余阶段与既有回执，不扩大范围或重复投稿 |
| 批量运行 | 批次预检读取各项目目标 | 每个项目保留其设置，顺序与并发由批次决定 |

## 实施与兼容约束

1. 先分离项目目标解析、制作依赖规划与发布交付规划，再接统一入口，不能只删除旧按钮。
2. 保留旧制作链API与历史任务恢复。旧 `auto_steps` 作为旧任务的兼容证据，不立即删除或重新解释。
3. 旧项目的 `produce/draft/publish` 保持原有副作用范围，不默认开启新增上传终点。制作目标从已有明确选择迁移；无法确定时展示待确认，不自动重建全部历史版本。
4. 不能只因项目已有BV就把保存的“仅制作／准备草稿”临时升级为原稿更新。现有 `ProjectRunPanel.preview()` 的已有稿件优先分支需要在统一入口中纠正。
5. 发布目标与原稿更新范围属于项目设置；既有不可变更新计划仍是某次已确认操作的记录，不能直接当作永远有效的项目默认值。
6. 批量与单项目读取同一项目目标。顺序发布仅增加跨项目调度，不再覆盖项目发布方式。
7. 每个发布提交继续使用预检指纹、幂等请求、运行门禁、结果未知核对和原有新BV确认，自动化验收不得真实投稿。

## 实现验收标准

- 一处修改步骤设置，项目运行与批量运行都读到同一结果；总览和预检没有第二份可编辑副本。
- 无中断任务时，一次打开预检、一次明确确认即可运行；检查不启动任务。
- 纯原声直用目标只规划其真实依赖，未选择的额外版本不被重制。
- 项目仅制作/准备草稿时，无论是否已有BV，都不发生远程上传或编辑。
- 上传后等待确认具有独立状态，恢复不自动投稿。
- 发布现有产物固定ID和哈希，工作稿变化不启动制作或暗换文件。
- 仅同步文案/章节不被无关制作依赖阻挡，章节使用正确分P快照。
- 继续旧任务保留旧终点，迟到预检与配置变化不能恢复失效确认资格。
- 多BV、多个项目、取消、超时、重复点击与未知提交结果均有明确处理。

## 实施记录与边界

- `assembly.target_version_ids` 与版本定义同一 CAS 保存；与发布分P列表独立。旧项目只有唯一版本或明确发布选择时兼容推导，否则要求在合成步骤明确目标。
- `publish.project_target` 只保存在项目，不继承全局/模板中的BV；现有原稿须明确CID与替换版本或同步范围，空替换映射不推导。
- 项目预检使用 `target_driven:true`，遍历实际版本的完整依赖链；依据每个生产步骤的输入指纹核对当前设置，复用有效结果。原声直用仅涉及获取视频与合成；只同步原稿资料无需制作。
- 发布页同一保存操作负责交付方式、账号、分P、文案与原稿目标；总览与新预检只读。仅中断任务额外选择旧计划恢复或按当前设置新执行。
- 单步页保留仅本步、运行到此步、从此继续项目；合成阶段使用版本选择生成局部成片，避免旧全版本依赖入口扩大范围。
- 普通批量按各项目设置执行。顺序发布专用命令只接受已保存为投稿且账号/合集/小节一致的项目，不在批次中覆盖这些设置；历史批次仍按原冻结范围恢复。
- 已有远端BV而明确另发新BV时，批量/顺序批次引导先用单项目入口完成重复投稿确认，不猜最近稿件，也不自动另发。这是目前的授权边界。
- 发布现有成品仍固定产物证据；只上传与只同步不改用新的工作稿。人工确认提交后父流程继续跟踪原任务。

本轮实际制作验收仅使用 8611 的隔离夹具，未向真实B站账号上传、投稿或修改稿件。完整测试与已修复的兼容问题记录在验收报告中。
