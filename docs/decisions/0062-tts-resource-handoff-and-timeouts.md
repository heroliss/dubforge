# 0062 — GPU 资源交接与配音请求超时

日期：2026-09-29

## 问题与实测

310 句配音在整步 7200 秒上限时仅完成 110 句。第 110 句 IndexTTS 推理耗时 621 秒，其中 s2mel 约 480 秒、声码器约 132 秒。前序音轨分离在 DubForge 进程内使用 CUDA，退出函数后未显式把 PyTorch 空闲缓存归还给独立运行的 IndexTTS 服务。

只重载空闲的 DubForge 后台、不重启 IndexTTS，使用相同句子、已保存参数与参考文件，在独立诊断目录生成第 110 句约 11 秒。第 109 句由约 97 秒降至约 7 秒。随机采样意味着不是逐采样点确定性基准，也没有据此保证整片速度；结果支持跨进程 GPU 资源竞争是本次主要诱因。

## 决策

- 音轨分离/转录运行函数退出后、释放步骤槽位和进入下游前，回收对象并归还本进程 CUDA 空闲缓存。进入配音时再兜底交接；不导入/初始化本来没有使用的 CUDA，不清理活跃张量或停止外部服务。
- API 独立返回 `stop_reason`（timeout/user），总览、步骤页和进度动态统一显示“超时停止中”或“正在停止”。
- IndexTTS 每次模型请求默认最多等待 300 秒，0 可关闭，支持全局/系列/项目继承。整步 7200 秒等时限依旧独立生效。运行保护不参与声音指纹，不让已有音频无故过期。
- 等待期间每 0.5 秒检查取消/整步超时。服务级错误直接停止整批，不对剩余句子继续排队。
- Gradio 的同步推理不会因为客户端 cancel 就保证停止。超时/取消后保留连接在后台观察，不接收迟到音频为正式结果。服务占用记录持久化，阻止新请求堆积；正常回执自动释放，断线或后台重载导致状态未知时提示等待或手动重启已管理服务。停止服务与启动新服务才能清除未知占用，不自动杀共享模型。
- 轻微超长（5% 以内、最多 150ms，保留已有 50ms 计时容差）不重复调用模型。仍保存真实时长和超长标志，不裁剪、不偷偷改写声音参数。

## 验证

隔离测试覆盖 GPU 交接顺序及异常、超时/用户取消区分、无进度时检查停止、服务未知占用与重启记录、迟到结果不得覆盖、服务故障停止整批、轻微超长提示、超时配置不破坏句级缓存。诊断脚本仅在独立目录生成少量样本，不写项目设置/成品或触发发布。
