# ADR-0077：全自动显存协调——配音服务按需自动停启

日期：2026-09-30。状态：采用。

## 背景

8GB 显卡上，IndexTTS 配音服务完成配音后模型常驻显存（约 7GB），后续项目的音轨分离（htdemucs_ft）启动即 CUDA OOM；反之分离/转写的大模型也会挤掉配音服务所需显存。此前依赖用户手动暂停/启动配音服务，与「全自动流程」的定位矛盾。用户明确要求：GPU 释放也应当是自动的。

## 决策

运行器在每个 GPU 组步骤开始前执行显存协调（`runner._prepare_gpu`）：

- **分离/转写步骤前**：设备空闲显存（`torch.cuda.mem_get_info`，设备级含其他进程）低于 `runner.gpu_free_reserve_mb`（默认 4096 MiB）时，自动停止**托管**配音服务释放显存并记日志；显存充足则不动（大显存卡零开销）。停止失败或仍不足时，由 ADR 补丁的「OOM 自动降级 CPU」兜底。
- **配音步骤前**：托管服务未在线则自动 `start()` 并轮询等待就绪（上限 `runner.tts_start_timeout` 默认 300 秒，模型首载较慢），超时以 `TTS_SERVICE_TIMEOUT` 明确失败（链挂起可恢复）；等待期可取消。
- **外部启动的服务不受管控**（无法安全代停/代启）：分离/转写前只提示「显存不足将自动降级 CPU」，配音前提示到服务页启动。
- 总开关 `runner.auto_tts_vram`（默认 true）；`false` = 完全手动管理。服务忙（正在配音）时 `stop()` 自身会拒绝——gpu 组互斥保证此刻不会有配音在跑。

设计取舍：不做「空闲 N 分钟后停服」的惰性策略——8GB 卡上配音服务与 htdemucs_ft 无法共存，停止时机由「下一步是否真的需要显存」决定（显存阈值判断），大显存环境自动零动作；每次停/启的模型重载成本由 gpu 组的串行化自然摊薄（不会在配音进行中途停服）。

## 验证

`test_runner_resources.py`：分离前低显存自动停服、显存充足不动、外部服务不代停、配音步骤前自动启动并等待就绪、总开关关闭时零动作。全量 1334 项测试通过。

## 已知约束

- 停/启发生在 gpu 组步骤边界，交替密集时每轮切换有模型重载开销（小显存卡 unavoidable——不重载就无法共存）。
- 显存测量依赖 torch；torch 不可用时跳过协调（返回 None），由 OOM 降级兜底。
