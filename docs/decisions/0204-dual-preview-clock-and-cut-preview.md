# 0204 双预览时钟、裁剪空缺与试听跳过

## 背景

成片剪辑同时展示原视频源时间轴和当前已生成成片。两者的时长可能不同，原因包括已保存的删除片段、编码起始偏移以及浏览器解码/缓冲延迟。若在两个播放器的每个 `timeupdate` 中互相写入 `currentTime`，两个异步时钟会反复抢占控制权，表现为拖动回弹、播放停顿数秒或两边逐渐漂移。

## 决策

1. **每次交互只允许一个播放主时钟。** 用户按下某一侧的播放、暂停或拖动后，该侧成为本轮会话的主时钟；另一侧只跟随。不要让两个 `timeupdate` 互相写回，也不要把播放中的对侧事件当成新的用户定位。
2. **定位和连续播放使用同一份已保存剪辑快照。** 原视频时间与成片时间通过 `sourceToOutputTime` / `outputToSourceTime` 映射；删除段内部的定位按明确的 `next` 或 `previous` 偏置收敛到接缝。未保存的剪辑草稿不会伪装成当前成片的时间轴。
3. **连续播放采用带滞回的追赶。** 小漂移只通过极小的 `playbackRate` 调整逐渐收敛；超过硬阈值才执行一次 `currentTime` 定位。每次定位必须等待目标媒体进入可播放状态或收到 `canplay/playing` 后再重试，且同一时间只保留一个待处理修正，避免反复 seek 造成卡顿。
4. **裁剪试听默认作用于源播放器。** 勾选“试听时跳过删除段”后，源时间轴播放进入删除区间时跳到该区间末端；暂停、拖动和逐帧定位不会自动跳转。若当前剪辑范围尚未保存，成片参考仍是上次已生成文件，应显示“成片尚未按当前草稿重制”，不把两者强行当作同一时间轴。
5. **加载/卡顿是可见状态。** 任一侧未加载、缓冲不足或发生媒体错误时，不阻塞另一侧，也不高频改写其时间；在播放器附近显示“等待成片载入/追赶中/已同步/时间轴只读参考”等状态。恢复 `playing/canplay` 后再执行一次待处理映射。

## 验收标准

- 播放 5 秒后两侧映射时间误差在正常解码条件下保持在约 120ms 内；出现短暂卡顿时不会反复跳回或暂停数秒。
- 删除段前、段内、段后的源/成片定位均按映射表稳定收敛；源播放器开启跳过试听时每个删除段只跳过一次，暂停和拖动不触发跳过。
- 用户拖动任一侧时，该侧立即接管主时钟；松手后的迟到 `timeupdate` 不会夺回控制权。
- 目标媒体暂时未就绪时不循环 seek；媒体恢复可播放后能够补做一次定位。
- 未保存草稿与已生成成片的时间轴差异在 UI 中明确，不把当前草稿的删除段声称已经出现在参考成片中。

## 不采用的方案

- 不用两个播放器持续双向硬同步，也不在每个 `timeupdate` 无条件设置另一侧 `currentTime`。
- 不在用户拖动时自动生成临时成片；临时渲染成本高且会混淆“当前草稿”和“已生成产物”的边界。需要精确核对当前草稿时，应保存方案后再生成新版本。
