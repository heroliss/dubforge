# 0115 — 统一运行入口与合集顺序发布批次

日期：2026-10-08

制作与已有草稿的衔接由 [ADR-0127](0127-batch-production-before-ordered-publication.md) 补充；发布记录的本地归档与回收见 [ADR-0128](0128-publication-record-lifecycle.md)。

## 背景

「运行制作步骤」使用当前勾选创建手动制作链，「检查恢复方案」使用上次保留计划；两者均预检、补齐依赖和复用产物，却以同级按钮展示。完整流程还包含评论、草稿、投稿及审核终点，不能只合并名称就把手动制作变成投稿。多个项目各自完成后进入投稿队列，也无法保证在合集中的日期顺序。

## 决策

- 项目列表和总览以「运行或继续…」选择执行意图。有保留计划时默认继续上次任务并显示终点；按当前勾选运行制作是明确的另一选项。总览可选择完整流程。统一入口复用现有制作、恢复和完整流程的权威预检与确认，不增加一套生产执行规则；具体计划仍分别保存，不能把新的制作成功解释为旧投稿流程完成。
- 引入持久化顺序发布批次，冻结有序项目 UID、目标账号、合集、小节、各项发布方案及确认指纹。来源日期用于初始排序，相同日期保持稳定顺序；未知日期明确要求手动核对，不用导入时间填充。创建待运行批次没有外部副作用，开始和恢复需精确指纹、请求 UUID、明确确认与当批素材权利确认。
- 批次在后端协调已有全流程及发布记录。首版依次补齐制作和发布，前一项的审核和合集核对完成后才推进后项；网页轮询仅展示状态，不启动后续任务。已有稿件沿用原记录，未知投稿回执暂停，禁止重新创建和自动重投。
- 同项目有原稿和审核修订草稿时必须明确选用哪份记录，选择进入预检指纹并冻结；历史稿件及其回执保持可查。创建回执丢失时保留 UUID 与原请求体，先按 UUID 只读查询；查询为空仍不能证明请求未处理，只能重试原请求。
- 已投稿原BV的当前合集位置以完整目标小节回读为准，严格核对账号、AID及BV，不能把原投稿快照当作现在的位置。已在目标小节的原BV走只读审核及成员核对路径，再参与最终排序；不启动历史投稿流程、不重新上传、不加入历史合集，原快照和回执保留。平台侧移动合集后无需为排序另投一稿。原视频替换是单独的编辑意图，当前由B站创作中心处理，不与顺序发布混用。
- 恢复预检把本次完整成员证据与原排序基线分别保存、纳入确认指纹；锁内离线核对沿用本次成员证据，不能用原基线重新推断当前归属。最终排序发送前再次核对复用原BV的当前审核；已有未知排序请求只核对原请求结果，不能重发或改写其基线。
- 同账号、合集、小节的活动批次互斥；活动批次占用其项目，普通制作、设置修改、归档等入口不能抢占。内部全流程必须按实际归属调用现有启动与发布锁，不能靠页面的禁用状态保护。
- 用户可要求本项完成后暂停；失败、审核退回、无法确认回执或远端成员变化转为需处理。恢复先重新预检并确认，复用有效产物和已有发布回执。程序重启保留批次并停止自动推进，不自行上传、投稿或重排。
- B站分P顺序与合集 episode 顺序是不同概念。合集排序读取完整目标小节、保存原成员顺序，把本批项目按确认顺序放到原成员之后；提交使用完整 episode ID 排列，写前校验远端快照，写后回读验证。其他成员或顺序发生变化要求重新确认，不覆盖外部修改。写请求单次发送，未知结果不自动重试。
- 未发送排序请求时可在恢复预检中明确确认新的远端基线；一旦发送状态不明，只读核对排列是否已完成。停止信号传递到排序请求，明确尚未发送可重新预检，无法确定是否发送则保留待核对记录。

## 平台依据

适配参考当前安装 SDK 的合集读取实现以及上游 [biliup season.rs](https://github.com/biliup/biliup/blob/master/crates/biliup/src/uploader/season.rs)：排序接口为 `/x2/creative/web/season/section/edit`，使用完整 `sorts` 列表中的合集 episode ID，与稿件 AID、BV 或分P CID 不同。平台接口可能变化，结构不完整时停止并返回可操作错误，不能把本地入队顺序视为平台排列已成功。

## 验证

隔离测试覆盖精确方案确认、原日期与手动顺序、重复请求、按序推进、失败暂停、既有回执与未知结果、重启恢复、活动批次占用、远端完整成员快照及重排回读。前端真实组件测试验证只读检查、双击防重、迟到响应、变更使确认失效、同一批次重试、暂停与恢复。本轮不对真实账号执行上传、投稿、加入合集或排序写入。
