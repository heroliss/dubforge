# ADR-0072：自动续跑链「挂起可恢复」与状态可视化

日期：2026-09-29。状态：采用。

## 背景与问题

手动勾选的自动续跑链（`params._chain`）此前把「剩余计划」和「是否自动续跑」耦合在一个字段里：任一步骤失败、用户取消、超时、未预期异常、强制结束，乃至进程重启（`recover()`），都会把链整个清空。后果：

1. 用户重试失败步骤成功后，链已销毁，无事可续——批量跑多项目时被迫逐步盯守；
2. 链状态对用户完全不可见（前端早已取到 `_chain` 但没有任何组件消费），还剩几步、为何停了无从知晓；
3. 存在暗坑：链挂起期间手动跑别的基础步骤成功，会意外触发续跑。

与之并存的完整工作流引擎（`WorkflowRun`，ADR-0049/0063）有自己的游标与恢复语义，本决策不合并两套引擎，只让手动链具备同等的「失败后可恢复」能力。

## 决策：计划与活性分离

`_chain`（剩余步骤列表，含正在运行的链头——**成功后才出队**）是计划；新增两个兄弟键表达活性：

- `_chain_state`：`active`（自动续跑中）| `held`（挂起，计划保留）。缺省视为 active，兼容存量数据。
- `_chain_hold`：`{step, code, message}`，挂起原因；kind 由 code 派生（`STEP_CANCELLED/FORCE_STOPPED`→已停止、`STEP_INTERRUPTED`→被中断、其余→失败）。

状态机（`runner._hold_chain/_activate_chain/_clear_chain/_continue_chain`）：

- `run_chain` 提交 → 写入完整计划并置 active。
- 步骤成功（默认 scope）→ 仅 active 时续跑链头；链跑空 → 三键全清，项目回到无链状态。
- 失败/取消/超时/未预期异常/强制结束/链头无法启动 → **挂起**：链头保留（B 表示法下它本就未出队），记 hold。
- 进程重启 `recover()` → 挂起而非清空（兼容旧数据：中断步骤位于链头之前的补回）。
- **明确放弃才清空**：新端点 `POST /{uid}/chain/stop`、工作流引擎 start/resume、试合成/选句合成/成品方案等特殊运行（保持原语义）。
- 恢复：`POST /{uid}/chain/resume`（active + 续跑链头）；或运行端点新增 `resume_chain: true`（随重试激活，成功即续跑，再失败再挂起）。普通重试（不带 resume_chain）不续跑——「仅重试本步」与「重试并继续」成为两个显式动作。

安全性不变：续跑永远由用户显式触发，且每步仍过 `DEPS_NOT_MET` 依赖门禁与 sha256 指纹校验，不会在坏状态上偷跑下游；挂起期间任何步骤成功都不会自动续跑（修掉第 3 条暗坑）。

## 附带修复：状态收尾的整行覆盖竞态

`_refresh_project_status` 原先「读整行→算聚合→merge 整行写回」，与链键写入并发时会把挂起前的旧 `params` 整体写回（多项目下偶发，测试中以约 50% 概率复现）。改为列级更新（`crud.update_project_status` 只写 `status` 列）。这是被新写入路径暴露的存量竞态，与链语义无关也可能影响其他 params 写入。

## UI 呈现

- 新组件 `ChainStatus`（总览页）：active 显示「⛓ 自动运行中 · 剩余: A → B → C」+ 停止后续自动运行；held 显示挂起原因 + 「重试并继续 / 放弃计划」。
- 步骤页：失败且挂起在本步时，主按钮为「重试并继续剩余步骤…」，原「重新运行本步」降为「仅重试本步」；链运行中页头加「⛓ 续跑中」标记。
- 项目列表（批量场景）：每卡分段条下一行紧凑链状态，挂起卡片提供「重试并继续」；选择栏提供「继续全部已挂起（N）…」批量恢复（逐项目显式确认，不做重启后自动续跑）。
- `GET /api/projects`（单个与列表）暴露计算字段 `chain = {remaining, state, hold?}`；前端 `utils/chainStatus.ts` 统一解析与文案，兼容旧 `_chain` 数组。

## 已知约束（不在本次范围）

- slot 等待占线程池线程、暂停中的步骤占住并发槽：约 7 项目接近 pool=8 的吞吐悬崖，可通过 `runner.pool_size` 调大。
- 工作流引擎与手动链仍互相清对方的键（引擎互斥，见 ADR-0049）。
