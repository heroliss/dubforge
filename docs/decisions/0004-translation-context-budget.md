# ADR-0004: 翻译请求使用上下文预算动态窗口与串行交接摘要

- 状态：已采纳（2026-09-20）
- 背景：旧实现固定按约 600 字符或 10 行切块。字幕行较短时会产生大量请求；“整篇翻译行数上限”也容易被误解为分块大小。长片的全局审校还可能把完整译稿重复放进每一次请求，无法稳定控制上下文。

## 决策

1. `translate.max_context_tokens` 作为每个翻译窗口的总安全预算，默认 200,000 token，面向约 1M 上下文模型保守使用 0.2M。
2. 请求预算先扣除系统提示词、编号纯文本协议指令、交接摘要空间和输出预留，再只用估算 token 数按字幕行装入窗口；行不会被拆开。窗口只有一个时发送整篇，多窗口时每个窗口一次完成翻译，并在同一响应中返回下一窗口使用的简短交接摘要。
3. 多窗口采用串行滚动，不再额外发起全文摘要请求，也不再设置翻译并发数。后一窗口拿到前一窗口的摘要后再开始，优先保证长文语境连续和限流稳定。
4. 翻译不再设置“两步直译”和“全局审校”阶段。模型在一次窗口请求中同时负责忠实理解、自然表达、术语和上下文衔接，减少重复 token 和限流风险。
5. token 估算使用保守的 Unicode 字符启发式，不绑定某一家模型 tokenizer。它只用于安全分窗，实际服务商仍以自己的 tokenizer 和上下文限制为准。
6. LLM 连接池和密钥仍由设置页统一维护；翻译与语义整理步骤均增加“模型配置”选择，空值表示沿用全局降级链，指定名称则固定使用该配置组。

## 后果

- 80 行、约 12,000 字符的普通字幕在默认配置下通常可以一次完成，不再因为旧的字符/行数门槛被切成二十多块。
- 非常长的字幕会根据正文 token 量和配置的上下文预算自动分窗；窗口数不再受独立行数门槛影响。
- 每个窗口只产生一个翻译请求，模型思考、译文和交接摘要在同一轮中完成，日志和页面可以直接展示该轮实时流式内容。
- 每完成一个窗口就原子更新一次 `translate.json`，步骤仍处于运行态时下游不会被放行，但翻译页可以实时显示已完成部分的视频字幕预览。
- 保守预算会牺牲一部分理论最大容量来换取稳定性。若服务商上下文较小，应把该值调低；若模型支持更大上下文，也应先在服务商侧确认实际限制后再调整。
