# 0223：恢复受理立即切换当前进度，并区分暂停批次快照

## 问题

恢复完整流程时，原先仅更新 `WorkflowRun.status/phase/error`，`execution` 仍保留上次失败的阶段、正文与计量。后台队列尚未执行新 worker 时，页面可以同时得到“已恢复”与旧失败进度。另一个独立问题是批次暂停后停止跟踪项目，条目缓存仍可能标为运行中；用户随后单独恢复项目时，这份历史缓存不能继续代表当前任务。

此外，完整流程线程池拒绝入队时，原 `_launch` 没有释放内存租约或结束已落盘的排队状态，会造成项目被无实际 worker 的流程占用。

## 决策

- 新启动、批次启动、制作恢复与原稿更新恢复，在受理事务中同时保存明确的 `workflow.queued` 进度。它表示受理后等待执行，不能伪装真实步骤运行或完成百分比。
- 新一轮执行重置耗时起点，保留有界旧历史；当前失败正文与旧计量清空。发布回执后的显式继续使用等待平台核对的阶段，不重新制作或投稿。
- 同一恢复 UUID 的受理回执继续永久保存。新 worker 之后再次失败，重送旧 UUID 只返回原流程现状；只有新的显式恢复请求才有新的入队机会。
- 单项目恢复与批次重新接管可以交替发生。批次刷新同一工作流的计划时合并原有永久回执，持久记录优先；公共预检未携带内部回执不等于清空它们，计划指纹与权利确认范围不变。
- `_launch` 入队失败时清理属于本流程的内存登记和项目租约，落盘失败原因并返回稳定的 `WORKFLOW_QUEUE_UNAVAILABLE`。受理回执仍保存，避免响应重送变成隐式再执行。
- 暂停、停止或待处理的批次，若历史条目仍为运行/监控，详情、列表与项目摘要均投影为该调度器的非活动状态。读取不修改工作流、步骤、Job 或发布状态，也不额外查询它们。
- 重启恢复时，批次中残留的活动条目同步落为暂停。已完成条目保留，其他分组独立推进。

## 验证

隔离测试覆盖直接恢复、旧失败历史保留、延迟队列受理、同请求重送、新 UUID 并发拦截、队列拒绝释放租约、再次显式恢复、已投稿回执边界，以及暂停批次各类投影不读取或修改真实工作流。真实模型与平台请求不参与这些回归。
