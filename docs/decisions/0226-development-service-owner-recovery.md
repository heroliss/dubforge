# 0226 开发服务身份登记与显式恢复管理

日期：2026-10-20

状态：已实现；当前已运行的旧控制台不会热加载本补丁，生产接管需另选空闲窗口执行。

## 背景

开发控制台原来仅保留 `System.Diagnostics.Process` 引用。维护时若在控制台之外替换后端包装器，旧引用不能管理新进程：重启会因端口已占用而拒绝，退出也可能遗留新后端。按端口猜测所有权或扩大进程树关闭范围会误伤其他实例及独立托管的配音服务。

## 决策

- `Start-DevService` 启动后，以 `dubforge.dev_owner` 记录明确的 PowerShell 包装器身份：工作区、前后端端口、角色、PID、创建时间、程序路径、完整 argv、服务命令和唯一 generation。登记放在 `data/dev-logs/<后端>-<前端>/<角色>.process.json`，不含配置密钥。
- 写入使用操作系统文件锁保护完整读改写事务，并以临时文件加 `os.replace` 原子替换。活进程登记不能被另一启动覆盖。清理同时比较 generation、PID 和创建时间，且只删除已退出进程的对应一代登记。
- 仅当原控制台引用已经退出或不存在时，才从登记恢复管理。核验 PID 创建时间、程序路径、完整命令行、编码命令中的工作区/角色/端口；若存在监听者，再核验预期端口属于包装器进程树、其 cwd 和服务入口均匹配。Vite 入口先解析 Windows npm 的 `.bin/../vite` 路径，再与当前项目的入口精确比较。
- 已登记包装器还在启动但尚未监听时，恢复为启动中，阻止重复启动。身份错误明确拒绝，不回退到端口或进程名接管。无登记、或已退出/身份已变化的旧登记不代表当前端口所有权，仍沿用原有未知端口占用拒绝逻辑。
- 单独停止、重启以及退出清理都使用相同的恢复入口。`BackendReused` 的外部后端始终不接管；`dubforge.dev_processes` 仍负责最终创建时间核验及独立配音进程树保护。
- 登记写入失败时保留刚启动的 Process 引用，当前控制台继续管理并提示其他控制台不能接管，避免因登记失败而遗失已启动的服务。

## 显式接管入口

`scripts/dev.ps1 -AttachRegistered -BackendPort <端口> -FrontendPort <端口>` 仅用于已有完整登记、原控制台已经妥善退出的服务。入口在任何目录创建、日志归档、端口清理及服务启动之前，先只读核验前后端全部登记和监听关系；任何一项不完整即中文拒绝并退出，不进入退出清理。全部核验通过才进入正常交互控制台，接管本身不重启服务；此后显式退出控制台会停止接管的前后端，仍保留独立配音服务。

该入口不是多控制台互斥锁，也不能撤回旧控制台内存中已有的 Process 引用。不得让仍管理同一服务的两个控制台并行操作；旧版本未登记的服务不会自动追认。维护工具可以通过同一 `register` CLI 登记自己刚启动且掌握创建时间的包装器，但必须先核验实际任务已空闲并正确退休旧控制台；不能仅凭监听 PID 补造登记。这里不新增 HTTP 管理/重启接口。

## 验证与生效边界

新增测试使用隔离工作区、8611 后端端口及假进程/PowerShell 拦截器，不操作生产服务。覆盖身份变化、跨工作区、外部监听者、Windows Vite 路径、并发写入、按代清理、登记失败仍保留 Process、复用外部后端、实际启动编码命令与协议一致、接管全量核验失败零清理，以及退出时恢复最新一代引用。

当前常驻控制台和服务无需、也没有在测试时被重启。补丁只在之后启动的新控制台生效；是否以及何时安全执行实际交接，需要结合当时任务、在途 TTS/提交请求和进程登记另行核验。
