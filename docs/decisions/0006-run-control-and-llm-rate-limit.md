# ADR-0006：运行代次控制与 LLM 限流冷却

## 背景

停止、暂停和强制结束是异步操作。确认弹窗打开后，原任务可能已经结束，甚至同一步已经开始了新一轮运行；如果控制请求只带步骤名，就可能把旧操作误发给新任务。另一方面，服务商返回 HTTP 429 时继续对同一个配置重试，会在没有成功可能的情况下拖慢整个管线，并让每个字幕片段重复刷出相同错误。

## 决策

1. 每次步骤运行创建一个 Job 代次。步骤清单返回当前 `job_id`，停止、暂停和强制结束请求可以带上该编号；编号不一致时返回 `stale_action`，服务端不执行控制动作。
2. 强制结束会立即把步骤标记为失败并终止可终止的子进程，但后台同步计算或正在等待的 HTTP 请求仍可能自然返回。旧 Job 收尾时会再次清理该轮登记产物；旧 Job 收尾前禁止同一步重跑，避免旧线程清理新线程的控制状态或写入新一轮产物。
3. 429 视为配置级短时限流：当前请求不再重试，立即尝试降级链中的下一组；收到 429 的配置在进程内冷却约 30 秒，冷却期间后续请求直接跳过。5xx 和读取超时仍使用退避重试。
4. LLM 调用接受可选取消检查，在请求返回、重试等待和发起下一次请求前检查；这样停止信号不会再进入下一次重试或降级请求。单次已发出的同步 HTTP 请求仍由其超时控制。
5. LLM 请求优先使用 OpenAI 兼容的 SSE 流式响应；服务商明确不支持流式时自动回退普通响应。步骤上下文把当前轮次的提示词、输出增量和状态写入独立 JSONL，步骤页以短轮询聚合显示，不让浏览器直接长期持有供应商连接。
6. 主动取消和强制停止在步骤详情、流程总览及侧栏以中性“已停止”呈现，不常驻红色错误横幅；执行器仍沿用可重试的失败状态和原有错误码，日志与任务记录保留。重新入队时清空上一轮错误，超时与真正失败仍显示错误提示。
7. 暂停请求和实际等待分开呈现：`pause_state=requested` 显示“正在暂停”，到达 `check_pause` 后变为 `paused`，显示“已暂停”。继续、取消和任务结束清除显示状态；保留原始运行状态与项目占用，避免暂停期间误启动第二个任务。

## 后果

- 过期弹窗变成安全的无操作，前端可以明确提示任务已结束。
- 限流场景从每个片段最多三次试探，变为一次记录后快速降级，日志和批量任务耗时明显降低。
- 强制结束后可能需要等待当前 HTTP 请求超时或返回才能重跑同一步；这是保证产物和控制状态不被旧线程污染的代价。
- 支持流式的服务商可以在首字节后实时看到模型输出；首字节之前仍受连接/读取超时约束。独立事件文件便于刷新页面和断线恢复，也不会把完整提示词混入普通运行日志。
