# 0230：项目列表先显示摘要，再独立核验产物

日期：2026-10-20

状态：采纳

## 问题

项目空间的首屏和定时刷新原来共同等待完整列表。完整列表需要真实核对每个项目的输入指纹、逐句产物和成片版本。一次实际六项目读取用时约16秒；把相同工作每5秒排入下一轮，会持续占用读取资源。此单次结果不能作为稳定性能基准。

## 决策

- 新增显式 `GET /api/projects?view=summary`，响应仍为数组，以 `X-DubForge-Projection: summary` 和每行 `projection` 标记合同。默认完整列表及真实运行预检保持原合同。
- 摘要只批量读取必要数据库列与正面的内存执行事实。不读取 Artifact、项目目录、媒体、逐句文件、评论状态文件、合集显示名缓存或完整任务配方。不请求平台或模型。全局默认配置仍按现有设置摘要读取一次。
- 摘要的 `dir_exists=null`、`freshness_known=false`、步骤 `fresh=null` 表示未知。非活动项目显示 `checking`，历史 `Project.status` 单列为 `recorded_status`。发布回执或历史 done 均不能证明产物当前有效。
- 明确的最新 Job、步骤、流程、批次及内存占用才可证明执行中；后读最新 Job 终态不能被较早读到的 StepRun.running 重新解释为活动。真实失败信息保持可见。
- `summary_revision` 是必要数据库配置与执行代次的摘要，不是产物指纹。它包含 Job/状态、流程游标、配置来源修订等，不含逐句心跳、进度、实时阶段文案和上传字节。前端仅在代次仍匹配时接受迟到的完整核验。
- 摘要与完整读取分别单飞，完成即释放，不缓存领域有效性。前端首屏不等待完整核验；摘要保持轻量轮询，完整核验独立单飞，按初次、手动、执行终态及低频间隔触发，普通定时器不为正在读取的完整列表重复排队。
- 旧后端忽略 `view` 返回完整数组时，前端按旧完整合同接收；不可因为摘要请求失败就持续重复重扫。

## 边界与验证

摘要只负责显示和导航，运行、发布、模板应用仍使用原有真实预检。它不能作为全局空闲或维护许可。文件在两次核验之间的外部变化仍需完整读取识别，不引入文件身份缓存或新鲜度 TTL。

隔离测试封锁产物、配置解析、目录和资料扫描入口；覆盖归档、坏 JSON、历史未知、活动与终态交叉读取、视图单飞隔离、修订失效和心跳稳定、数据库查询数不随项目数增加。前端另测首屏时序、完整读取节流、旧接口兼容和迟到响应保护。实际首屏体验须在新后端可安全加载后再验证；不据此宣称完整核验端点提速。
